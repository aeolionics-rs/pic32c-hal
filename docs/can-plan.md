# can-hal-mcan: plan

*History: the plan the M_CAN driver was built to in experiments/can-hal-mcan, kept as written. The driver is now this repository's `pic32c-hal::can` (feature `can-hal`), its bench programs `examples/pic32ck-curiosity-ultra`'s `can_loopback`, `can_ping` and `can_echo`.*

A can-hal backend for the full Bosch M_CAN, with the same public shape as
`can-hal-fdcan` (confirmed transmission, receive events, bus status,
recovery, statistics), and frames stamped with the controller's own
timestamps: `Sent(at)` from the Tx event FIFO's TXTS, received frames from
RXTS. First target: the PIC32CK SG01 Curiosity Ultra. Later: the PIC32CM GC
(the same M_CAN behind a Microchip wrapper, plus a 32-bit timestamping unit),
the STM32H7 and the SAM E5x.

## The board: EV33A17A, PIC32CK SG01 Curiosity Ultra (DS70005529)

- PIC32CK2051SG01144: Cortex-M33, 120 MHz, 2 MB flash, 512 KB SRAM.
- On-board debugger: PKoB4 (MPLAB mode as shipped; switches to CMSIS-DAP
  with `pycmsisdapswitcher`), with a virtual COM port.
- CAN0: PB16 (TX) and PB17 (RX) to U701, an ATA6561 (CAN FD up to 5 Mbit/s,
  DS20005991B), its STBY tied to ground, so always in normal mode. Bus on
  J704: 1 CANL, 2 GND, 3 CANH. SW700 looks like the termination switch (two
  62 Ω, split); to confirm before connecting.
- CAN1: PB23/PB24 to U702, on J705.
- On the FD bus with the SH-C31A and SH-C31G (both ends terminated), the
  CK's termination stays off.

## The controller (DS60001795, chapter 39)

- CAN0 at `0x4501_E000`, CAN1 at `0x4502_0000`.
- Bosch's register layout from offset 0, with `MRCFG` at 0x08 (message RAM
  base: `OFFSET`, bits 23:16, plus bus QoS) where Bosch has `CUST`. No
  Microchip wrapper here (the PIC32CM GC puts the same registers at 0x100,
  behind interrupt-flag, `SYNCBUSY` and write-protect registers).
- Message RAM in system SRAM, up to 4352 words, its sections placed by start
  address (`SIDFC`, `XIDFC`, `RXF0C`, `RXF1C`, `RXBC`, `TXEFC`, `TXBC`) with
  element sizes in `RXESC`/`TXESC`. Elements are the same format as ST's.
- Interrupts in Bosch's numbering (TC 9, TCF 10, TEFN 12, TSW 16, EP 23,
  BO 25, PEA 27, PED 28, …), on two lines (`ILS`/`ILE`). CAN0's NVIC number
  looks like 79, CAN1's 80: to confirm.
- Clocks: kernel clock from GCLK peripheral channel 39 (CAN0) / 40 (CAN1),
  bus clock enabled by `MCLK.CLKMSK0[13]` (CAN0). An 80 MHz kernel clock
  gives 16 time quanta per bit at 5 Mbit/s and the same timings as the
  G431.
- Timestamps: the 16-bit counter (`TSCC`/`TSCV`), counting bit times with a
  prescaler of 1 to 16, captured at start of frame into RXTS and TXTS. It
  wraps every 65,536 counts (131 ms of bit times at 500 kbit/s), which the
  driver has to extend (below). No timestamping unit on the CK.
- Transmitter delay compensation (`TDCR`) as on ST's FDCAN.

## The driver

- Same structure as `can-hal-fdcan`: `Can<C, N>`, a `static State`,
  `on_interrupt` from the line 0 handler, `Config` and `BitTiming`, the
  ordering of reports (`order.rs`), frames to and from elements
  (`frame.rs`), and the single-shot failure watch on the timeout counter.
  Copied first; a shared crate later, once both drivers settle.
- Registers: Bosch's layout and interrupt bits, in its own `registers.rs`.
- Message RAM: a layout chosen at build time (filter, FIFO and buffer counts
  and element sizes, through const generics or a const layout) in a buffer
  the application provides as a `static`, whose address goes to `MRCFG` and
  the start-address registers. To start: no filters (accept all into FIFO 0,
  as `can-hal-fdcan` does), a Tx queue of a few buffers, a Tx event FIFO of
  the same depth.
- Timestamps: at each interrupt the driver reads `TSCV` with `C::now()` as an
  anchor and converts each RXTS/TXTS to `C::Instant` by its distance back from
  that anchor, in bit times. With TSW enabled the anchor is never more than
  one wrap old; a frame older than one wrap at handling would be ambiguous,
  so the interrupt latency budget is one wrap (131 ms at 500 kbit/s). The
  same would work for `can-hal-fdcan`, whose `Sent` uses the interrupt time
  today.
- Filters, FIFO 1, dedicated Rx buffers and the GC's timestamping unit
  later, each with its own API.

## The bench crate (`pic32ck-curiosity-ultra`, now in pic32c-hal's `examples/`; the CAN programs are `curiosity-can` here)

- Target `thumbv8m.main-none-eabihf`; `cortex-m-rt`; `memory.x` from the
  data sheet's memory map (flash and SRAM addresses to confirm, and any
  boot ROM handshake, as the PIC32CM SG00 has).
- PAC: svd2rust 0.37 from the `Microchip.PIC32CK-SG_DFP` 1.11.288 pack's
  SVD, generated by `pac/generate.sh` (with `fix_svd.py` for any fixes the
  SVD needs). Check the pack's licence before committing the SVD or the
  generated PAC.
- Clocks ourselves: 120 MHz CPU, a GCLK generator at 80 MHz for CAN0, from
  the PAC.
- Debug and flashing: CMSIS-DAP (switch the PKoB4 first), then probe-rs
  with a `target-gen` target from the pack for defmt over RTT; pyOCD with
  the pack as the fallback.
- `Clock` for the driver from the DWT cycle counter, extended to 64 bits;
  an executor only if the tests need one (`embassy-executor` with no time
  driver, timeouts from the same counter).

## Steps

1. Tooling: download the pack, generate the PAC, switch the PKoB4 to
   CMSIS-DAP, get a target for probe-rs (or pyOCD), and blink an LED with a
   defmt line.
2. Clocks: 120 MHz CPU, 80 MHz for CAN0, checked with a timer or the counter.
3. `can-hal-mcan`: registers, message RAM layout, configuration, interrupt
   handling, internal loopback. The bench's loopback tests are
   `nucleo-g431kb`'s: every classic and FD frame, three at once with an
   abort, classic only.
4. Timestamps: anchor and conversion; `Sent` and `Received` in bus order
   with monotonic stamps; the wrap.
5. On the FD bus (J704 to the SH-C31A/G bus, termination off): classic and
   FD both ways at 500k/2M and 500k/5M, then the error-handling set
   (single-shot, bus-off on an H-L short, bus error frames, listen-only).
6. Later: filters, the PIC32CM GC (wrapper, timestamping unit), a shared
   core for `can-hal-fdcan` and `can-hal-mcan`.

## Confirmed (2026-11-14, DS60001795H and the bench)

- CAN0's interrupt is NVIC 143 (CAN1 144), one line for LINE0, LINE1 and
  the ERROR line. Pins: function H (PMUX 7), PB16 TX and PB17 RX on the
  boards. Kernel clock up to 100 MHz (GCLK channel 39); bus clock
  `MCLK.CLKMSK0[13]`, on at reset.
- `MRCFG.OFFSET` is eight bits (23:16): the message RAM's base is
  `0x2000_0000 + (OFFSET << 16)`, so any SRAM, and every section within
  one 64 KiB block; the start-address fields are byte offsets in it (bits
  15:2). `ERROR` at 0x100 (BERR, message RAM bus errors) is Microchip's;
  BEC/BEU aren't implemented. CREL reads 0x3230_0000.
- No `CAN0_SEC` view: on the SG01 only PORT and EIC have Secure aliases.
- Flash and SRAM as in `memory.x`; boot via BFM's first two words.
- SW700 switches the split termination (commons 2/5 to pins 1/4, CANL and
  CANH); the guide doesn't say which slide position is on, so check with a
  meter: about 124 Ω across J704 pins 1 and 3 with it on.
- The PKoB4 switches to CMSIS-DAP as the SG00 board's does.
- There is no basic TC: the timers are TCC0-TCC3 (32-bit) and TCC4-TCC7
  (16-bit), and the RTC. TCC0 and TCC1 share GCLK channel 23 (table 20-2;
  the TCC chapter's setup steps say 31). Reading COUNT takes a `READSYNC`
  command: about 1 µs a read with the cycle-counted overheads, at 16 MHz.
- Flash (FCW): unlock with KEY `0x91C3_2C01`, then CTRLA.NVMOP, holding
  the FCW mutex (`0b011`, shared with the HSM). ADDR takes the system
  address (`0x0C..`). Both boards' fuses (FUCFG6 `0x70`) leave ECC in
  bypass (ECCCTL 3) and unlocked: quad and row writes still store ECC, reads
  don't check it. PWP, LBWP and the PAC protect nothing after boot. The
  CMCC's CTRL reads 0 whatever its state; SR.CSTS is the state.
- WDT: the SAM D5x one, at 0x4401_6000, IRQ 11, from the 1.024 kHz
  OSCULP32K; off at boot on both boards (FUCFG0 0). RSTC.RCAUSE at
  0x4400_A000 (a pyOCD reset reads as `SYST`). The unique ID is a version 4
  UUID at CAL OTP + 0x1E0 (`0x0A00_71E0`), in RFC 4122 byte order.
- The CMCC (4 KiB L1 cache) is off out of reset. Turned on, an embassy
  timer wakes about 7 µs late instead of 13.

## Done so far

The PIC32CK drivers other than CAN were separate crates until 2026-11-14,
then merged into `pic32ck-hal`, one module each; all reran on both boards
after the merge. The same day they moved, with the PAC and their bench
programs, to their own repository, aeolionics-rs/pic32c-hal (crate
`pic32c-hal`); the CAN bench reran against it.

- Clocks: 120 MHz CPU, 80 MHz on generator 2, 48 MHz on generator 3, from
  the 12 MHz crystal through PLL0 (960 MHz VCO).
- `can-hal-mcan`, classic frames: internal and external loopback, and
  250 kbit/s on a bus between the SG01 and the GC01 (ping/echo), all
  passing. Timestamps still use the interrupt time, as `can-hal-fdcan`'s
  `Sent` does; the RXTS/TXTS conversion (step 4) is still to do, as are
  filters, bus-off recovery on a real bus, and single-shot on this
  controller.
- CAN FD (2026-11-14), at parity with `can-hal-fdcan`: `Config::with_data`
  (`BitTiming::solve_data`, transmitter delay compensation for data
  prescalers up to 2), `ConfirmedTransmit<Frame>` (and `<CanFrame>`),
  `ReceiveEvents<Frame>`, `Error::FdDisabled`. Message RAM in two kinds:
  `ClassicMessageRam` (8-byte data fields, 512 bytes, for the small parts,
  a C21's 32 KiB of SRAM among them) and `FdMessageRam` (64-byte, 1,792
  bytes); a data phase with classic RAM is `Error::FdNeedsFdRam`. Both
  boards: loopback (internal and external) passes with every classic frame
  and every FD frame and eight 64-byte FD frames at once with an abort, the
  FD channel reconfigured as classic refuses FD frames, and the classic RAM
  build (`LOOPBACK_CLASSIC=1`) passes and refuses a data phase; on the bus
  between them, `ping`/`echo` pass classic at 250k (720 frames each way)
  and, built with `CAN_FD=1`, FD at 500k/2M and 500k/5M (`CAN_FD_DATA`;
  1,360 frames each way, every length with and without BRS), no bus errors.
- Acceptance filters (2026-11-14): `Filterable`, exact or `TooManyFilters`
  (never merged), 8 standard and 16 extended classic (ID and mask) filter
  elements in the message RAM (classic 608 bytes, FD 1,952). GFC rejects
  frames matching none; with no filters set each list's first element
  accepts everything, so filters change in RAM while the channel runs. The
  RAM is no longer aligned to its size; `Can::new` checks it stays inside
  one 64 KiB block. Both boards, FD and classic builds: loopback's filter
  test passes (one standard ID, a masked extended range, FD frames, too
  many refused, cleared); ping/echo classic on the bus still passes.
- Filters at init time and live (the user's convention, 2026-11-14): what
  the hardware can only set at init goes in the configuration, what it can
  change live goes through `Filterable` on the channel. Here: the RAM types
  take their filter room as const generics (`ClassicMessageRam<S = 8,
  E = 16>`, so a build that filters extended identifiers only can take
  `<0, 16>`, 576 bytes);
  `Config::with_filter_lists(standard, extended)` sets the list lengths in
  use (default all; longer than the RAM is `FilterListsTooLong`; a length
  of 0 leaves that kind unfiltered, all accepted); `set_filters` is exact
  within those lengths or `TooManyFilters`. Filters survive a reconfigure
  that keeps the lengths. Both boards, both builds, pass.
- `pic32c-hal::usb`: CDC-ACM echo on J203.
- `pic32c-hal::flash`: on both boards, page erase 19.4 ms, a 1 KiB row
  write 3.4 ms, a 32-byte word write 110 µs; data reads back from rows,
  words, and runs mixing both; refusals of misaligned and out-of-range
  requests. Busy panel 2: the CPU runs on (8 SysTicks in a 4-page erase).
  Busy panel 1, the program's: the CPU stalls with the cache off (no
  SysTick until the end), and runs from the cache with it on.
- `pic32c-hal::wdt`: on both boards, start and stop, refusals, no early
  warning when fed every 100 ms, one a period when fed every 750 ms, and
  when starved an early warning at 498-501 ms and a reset about 1 s in,
  after which RCAUSE reads `WDT`.
- `pic32c-hal::time`: embassy-time at 1 MHz on TCC0, from 16 MHz on generator
  4. On both boards, with the cache on: no timer early, `now` never back,
  2,000,003 ticks in 2,000,003 µs of cycles, timers 7-10 µs late (8
  tickers falling due together, up to 48 µs), far timers (2,000 and
  4,000 s) not firing early; and the same across 2^31 and 2^32.
